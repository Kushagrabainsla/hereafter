# Multiplayer architecture

The playable network slice uses invite-based rooms. `src/network/peerRoom.ts` opens a Trystero room using a 10-character random room code. Trystero's default public Nostr relays exchange connection information; gameplay packets travel between browsers over WebRTC data channels. GitHub Pages serves only static files. There is no project-operated room server or per-session map request.

Each browser renders the arena locally. `src/game/playerController.ts` supplies its local pose at up to 20 updates per second. The versioned `pose-v1` action includes an arena key, sequence number, location, view, jump height, and movement flags. Receivers reject out-of-order, malformed, or wrong-arena packets. `src/game/remotePlayers.ts` interpolates remote avatars between updates. Each peer computes a spawn slot from the sorted connected peer IDs so newly joined players do not occupy the same point. The room link includes the current arena URL parameters.

`src/game/combatRules.ts` defines the starting knife, pistol and carbine, deterministic pickup positions, weapon range and damage, and a simplified line-of-sight check against gameplay colliders. `src/game/matchState.ts` owns health, inventory, ammo, reloads, kills, deaths, respawns, and 30-second pickup returns. The lowest connected peer ID temporarily coordinates combat. Other peers send attack and pickup intents; the coordinator checks range, cover, ammo, cooldown, and proximity before broadcasting a versioned combat snapshot. Peers retain the latest snapshot so another can take over when the coordinator leaves. `src/game/weaponVisuals.ts` renders held weapons and street pickups.

This is a prototype authority model. Positions still come from clients, so a modified client could move illegally. The coordinator is chosen deterministically but has no heartbeat or epoch-based handoff yet; contested joins and abrupt disconnects need more testing. The next networking step is input-based movement validation and a durable authority handoff. A connection may also need a TURN relay when direct WebRTC cannot cross a particular network; the public signaling relays do not supply that relay. Their availability is outside this project's control, so production matchmaking needs a monitored signaling and TURN plan.
